# MTH1W accessibility and usability review evidence

This directory stores **qualified-human accessibility/usability review evidence** for the exact current MTH1W accessibility targets generated by:

```bash
python tools/mth1w_accessibility_review_evidence.py plan --output /tmp/mth1w-accessibility-review-plan.json
```

The current plan has two independent target classes:

- **43 lesson-alternative targets** — each binds the exact authored lesson digest plus the deterministic learner and answer-key Markdown export digests;
- **4 learner-application surface targets** — Android, Windows, macOS, and iOS each get a separate target binding the exact current learner-facing Flutter source surface used for Home, curriculum reference, Grade 9 Math learning, draft units, home-learning guidance, and local practice.

A review of a printable Markdown lesson does **not** review the Flutter application. A green Flutter test/build does **not** review a human learner's assistive-technology experience. An Android accessibility review does not establish Windows, macOS, or iOS accessibility, and the same rule applies in every direction. All 43 lesson targets plus all four platform targets must have current human approval before the accessibility gate can become eligible for promotion.

The platform targets reflect current build-evidence lanes only. Their presence does not claim App Store readiness, signed release readiness, production support, or accessibility conformance.

## Evidence rules

Each submitted `*.json` file must conform to `schemas/accessibility-review-evidence.v1.schema.json` and must:

- preserve the exact `target_id`, lesson/unit identity, platform identity where applicable, and `target_sha256` from the current generated plan;
- identify the human reviewer and relevant qualification;
- record an offset-aware review timestamp;
- record the actual assistive technologies, devices, document tools, operating systems, themes/scaling settings, or other environments used in `tested_environments`;
- use only the confirmation fields required by that target scope;
- preserve findings, including negative findings, with severity and disposition;
- use `changes-required` or `rejected` when the current surface is not acceptable;
- use `approved` only when every in-scope confirmation is true and there are no open or unresolved major/critical findings;
- keep `attestation_type` equal to `human-accessibility-usability-review`.

Do not edit a generated target digest or platform field to make an older judgement apply to changed content or a different operating environment. If a lesson, export, bound learner-app file, or platform-scoped target changes, regenerate the plan and review the new target revision.

## Claim boundary

This evidence system can record qualified-human findings and approvals. It does not itself establish WCAG or AODA legal conformance, Ministry approval, course completion, grade/credit status, App Store/signed-release readiness, production support, or universal usability across every disability, device, assistive technology, language, theme, scaling setting, or context. Those claims require evidence appropriate to their actual scope.
